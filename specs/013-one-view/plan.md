# Implementation Plan: One View, Four Regions

**Feature**: `013-one-view` | **Spec**: [`spec.md`](./spec.md)
**Date**: 2026-09-07 | **Depends on**: 007 (the row), 008 (the footprint), 010 (counterfactuals)
**Milestone**: the first beat of SRD-v2. It opens the surface beats and it moves no number.

## Summary

The application becomes one non-scrolling viewport of four regions — controls left, the
horizon row centre, each panel's scores in that panel's own column beneath it, the last
selection right. Nothing new is computed. The claim that nothing new is computed is the
expensive part, and it is bought first: a gate that digests every computed quantity of the
recorded case and refuses any change to any of them, landed and watched failing before the
first element moves.

## The order this beat is built in, and why it is not negotiable

FR-001 says the gate lands first. That is not a preference about test-first discipline. A
1,301-line component whose presentation and computation have never been separated is about
to be taken apart; without a committed record of what it currently computes, "the refactor
changed no numbers" would be an assertion by the person who did the refactoring, which is
the one witness this project never accepts.

1. **G-07 lands green over the tree and red over a planted coefficient.** No layout file is
   touched in that commit.
2. Then the regions, then the scores in their columns, then the detail region, then the
   floor. G-07 runs on every one of those commits.

## Where the record lives, and why not in `data/`

The record is `scripts/gates/records/surface-invariance.json`: one entry per computed
quantity, its digest, and the sentence naming what produced it.

`data/` is for artefacts converted from upstream by `data/scripts/convert.py` and held by
G-01; putting a digest of *this repository's own code* beside them would invite the two to be
regenerated by the same command, which they must not be — G-01 asks whether the conversion
still produces the committed bytes, and G-07 asks whether the code still produces the
committed figures. They fail for different reasons and are re-recorded by different people at
different times. The record therefore sits with the gate that owns it, inside an existing
top-level directory. No new top-level directory is proposed.

## What is digested, and what that exposes

The producer walks the recorded case from the declared seed through every module that
computes anything, and digests each result:

| Quantity | Producer |
|---|---|
| the declared configuration | `digestOf(config)` |
| initialisation, and state bytes at step 0 and after the declared advance | `initialiseFromTruth`, `Run.advance`, `stateBytes` |
| published results and their invariants | `publishResults` |
| every instrument's observations | `sampleSurface`, `sampleXbtDrops`, `argoObservations` |
| the analysis field, its attribution weights, its used and excluded sets | `analyse` |
| each declared horizon's forecast field | `runForecast` |
| the departure brief | `departureBrief` |
| each declared horizon's score, both skills and all three errors | `score` |
| the observation footprint a panel reads | `footprintOf` |

The last two rows are where the entanglement the spec expects becomes visible, and both are
recorded as findings rather than resolved quietly:

- **The per-horizon scores have no headless producer.** `HorizonRow.scoreAll` computes every
  panel's `Score` inside a React component and keeps it in component state, so today the only
  way to obtain the figures the surface shows is to render the surface. The gate re-derives
  them from `runForecast` and `score`; the beat then lifts `scoreAll` onto exactly that
  derivation, and the gate is what proves the lift changed nothing. This is finding 2 of the
  spec — *a computation that happens because something is drawn* — and it is the reason the
  gate had to come first rather than the reason it can be skipped.
- **`footprintOf` is called three times per render** from `App.tsx`, uncached, plus once more
  inside `HorizonRow`. Same finding, second instance.

## Decisions this plan makes

- **The grid is CSS grid with four named areas, and the column count comes from
  `horizons.leadHours.length`** (FR-012), handed to the stylesheet as a custom property the
  way beat 007 hands it the row geometry. A configuration with five or seven horizons lays
  out without a code change.
- **The scores are not a table.** Each panel's figures render inside that panel's grid
  column, in a `scores` row that shares the grid's column track with the row above it, so the
  alignment is structural rather than arranged. The existing `score-panel` section is removed,
  not hidden — FR-006 says no scores table exists elsewhere.
- **The narrative sections stay for now.** FR-42 is beat 014's, and deleting them here would
  put this beat in the business of moving prose. They move behind the controls region as
  reachable disclosures until 014 takes them off the application entirely; what this beat
  removes from the first viewport is their claim on vertical space.
- **The floor is measured, not chosen** (FR-010, and SRD-v2 §9). A Playwright measurement
  walks the viewport down until a panel falls below `minimumPanelWidthPx` or a region's
  content exceeds its box, and prints the width and height it found. Those two figures are
  then declared in `presentation` as `minimumViewportWidthPx` and `minimumViewportHeightPx`,
  refused by the schema if they cannot hold the declared horizons, and read by both the
  application and the tests. No literal appears in a component or in CSS.
- **Below the floor the application does not shrink the row.** It states the size it needs as
  a `Declared` figure and offers the single-panel presentation, which is FR-49's enlargement
  reached as a fallback. 015 makes enlargement a proper selection; this beat needs only that
  the fallback is operable, and says so.
- **Internal scroll is declared, not accidental.** A region that may scroll within itself
  carries a `data-scrolls` attribute, and the no-scroll test asserts that every element with a
  scrolling overflow is one of the declared ones. An undeclared scrollbar fails the test by
  name.

**Result: PASS.** No Complexity Tracking entry.

## Risks this plan accepts

- **The walkthrough of beat 011 resolves DOM anchors by test id.** Moving every section
  breaks it. It is updated in the same commit as the regions, and its shell test is the
  detector.
- **`fullPage: true` screenshots stop meaning anything** once the page is one viewport. The
  screenshot suite moves to the declared floor and the declared reference width.
- **The domain choice of SRD-v1 FR-11 has no control today** — `App.tsx` reads
  `domains.defaultId` and nothing offers the second domain. FR-004 puts it in the controls
  region, so this beat builds it. It changes no computed quantity for the recorded case,
  which is the default domain, and the gate holds that.
